# 의사결정 로그 (Decision Log)

이 프로젝트에서 "왜 이렇게 했는가"를 기록하는 append-only 로그입니다. 겉보기엔 버그나 비효율처럼 보이지만 **의도된** 설계 결정들을 남겨, 미래의 나 또는 코딩 에이전트가 근거를 모른 채 되돌리는 일을 방지합니다.

## 작성 규칙

- **삭제하지 않습니다.** 결정이 바뀌면 새 항목을 추가하고 이전 항목의 `상태`를 `대체됨 (→ 아래 날짜)` 으로 바꿉니다.
- 새 항목은 **맨 위**(최신순)에 추가합니다. 날짜가 불명확한 초기 결정은 최하단 "초기 설계 결정"에 둡니다.
- 항목 템플릿:

```markdown
## YYYY-MM-DD — 한 줄 제목
**결정:** 무엇을 하기로 했는가.
**이유:** 왜. (트레이드오프 포함)
**영향:** 이 결정이 강제하는 것 / 건드리면 깨지는 것.
**상태:** 유효 | 대체됨 (→ YYYY-MM-DD)
```

## 2026-08-25 — 태그 랭킹 페이지: 순위 테이블 폐기, 4분면 지형 분류로 재설계

**결정:** 태그 랭킹 페이지를 "오늘 어떤 태그가 통했는가"라는 인사이트 전달 구조로
재설계했다. 전체 순위 테이블은 제거하고, 태그를 **사용량(등장 작품 수) × 성과(상위권
집중도)** 4분면으로 분류해 지형 지도 + 구역별 카드 + 브리핑/무버로 보여준다.
구역: 대세(주류·강세) / 숨은 강자(니치·강세) / 과포화(주류·약세) / 약세(니치·약세).

**기준(바꾸면 분류가 흔들림):**
- 주류/니치 경계 = 그날 등장 작품 수 분포의 **P75**. 고정 숫자는 표본이 300→500으로
  바뀐 과거 날짜에서 깨진다.
- 강세/약세 경계 = **집중도 1.0** (상위 100위 안/밖 등장 비율이 같은 지점) — 설명이 자명.
- 등장 5작품 미만은 분류 제외(적재 단계에서 이미 집중도 미계산). 검색으로는 조회 가능.
- 구역별 정렬 기준이 다르다: 대세=인기 점수, 숨은 강자=집중도, 과포화/약세=사용량
  (많이 쓰는데 안 통하는 것이 더 중요한 정보).

**집중도 축 상한은 8로 고정한다(클램프).** 집중도의 이론상 최대는 400(분모를
`max(하위400, 1)`로 깔았기 때문)이고 실제로도 이상치가 잦다 — 2026-08-25는 최대 16.0인데
2위가 4.8이었다. 축을 그날 최대값에 맞추면 이상치 하나가 나머지를 눌러 **중앙값이 축
높이의 24%까지** 내려간다. 상한 8로 고정하면 여러 날짜 실측에서 클램프되는 점은
**날짜당 1개**뿐이고 중앙값이 37~40%로 올라오며, 날짜가 바뀌어도 축이 같아 어제와
눈으로 비교된다. 8 초과 태그는 **▲(삼각형)으로 축 상단에 고정**하고 정확한 값은
툴팁·구역 카드에 남긴다. 도메인 상한은 9.2로 클램프 값보다 크게 둔다 — 8에 그리면
마커가 축 경계에 걸려 잘린다.

**지도 라벨은 충돌 회피로 배치한다.** 원 68개 중 겹치는 쌍이 27개라 미리 고른 태그에
무조건 라벨을 붙이면 서로 겹치거나 남의 원에 얹힌다. Recharts가 shape에 넘겨주는
`data-recharts-item-index`로 렌더 패스 시작을 감지해 배치 기록을 비우고, 실제 좌표
(`cx`,`cy`)로 우선순위 순(인기 점수 순위 + 집중도 순위 정규화 합) 훑으며 **이미 놓인
라벨과 겹치지 않을 때만** 배치한다. 결과 라벨 8개 → 14개, 겹침 0. 클램프된 점은 축
상단에 있어 위쪽에 구역 이름이 있으므로 **라벨을 아래쪽에만** 둔다.

**집중도 축은 Recharts `scale="sqrt"`가 아니라 "제곱근 공간의 선형 축"으로 만든다.**
값을 미리 `Math.sqrt()`로 변환해 **linear 축**에 올리고, 눈금은 `LIFT_TICKS.map(Math.sqrt)`
위치에 두고 `tickFormatter`로 제곱해 실제 집중도 값(0, 0.5, 1, 2, 4, 8)으로 표기한다.
눈금 간격은 sqrt 스케일과 완전히 동일하다.

그렇게 하는 이유는 **sqrt 스케일이 음수 도메인을 못 쓰기** 때문이다. 집중도 0
(상위 100위 미등장) 태그는 원의 중심이 x축 선에 놓여 아래 절반이 잘렸는데(실측 6개),
sqrt 스케일에서는 도메인을 0 아래로 내릴 수 없어 `YAxis padding`으로 우회해야 했다.
그런데 4분면 배경(`ReferenceArea`)은 **데이터 좌표로 그려지므로** padding만큼 플롯
위아래에 색 없는 띠가 남았다. 선형 축으로 바꾸면 도메인을 `[-0.3, √9.2]`로 내릴 수 있어
원도 안 잘리고 배경도 플롯을 빈틈없이 덮는다.

- 4분면 경계는 `LIFT_MID = 1`(= √1). 배경은 `LIFT_AXIS_MIN`~`LIFT_MID`,
  `LIFT_MID`~`LIFT_AXIS_MAX`로 도메인 끝까지 채운다.
- X축 도메인 여유는 `[min×0.78, max×1.6]`. 가장 많이 쓰인 태그는 인기 점수도 가장 높아
  원이 제일 크므로(반지름 최대 17px) 좁은 화면에서 오른쪽 경계에 스쳤다.
- 회귀 확인 항목: 폭 360/390/768/1200/1440 × 다크·라이트 × 여러 날짜에서
  ① 경계를 벗어난 도형 0개 ② 4분면 배경의 상·하단 여백 0px ③ 라벨 겹침 0쌍.

**제약:** `TagCountsTop100`은 **2026-04-13 2-track 개편부터** 존재한다. 그 이전 날짜는
집중도가 전부 없어 4분면이 불가능하므로 인기 점수 순 목록으로 폴백한다(사유 문구 포함).
검색은 지도에서 비일치 태그를 흐리게 하고 결과 칩을 따로 보여준다.

**상태:** 유효

  방식을 먼저 구현했는데, 59개를 배지 방식과 교차 검증해 **2건이 어긋났고 둘 다 성인작을

  걸리는 것으로, 성인작이라도 표지가 무해하면 실제 표지가 나온다.

- **태그로 판정하지 않는다.** 태그는 작가가 붙이는 값이라 등급과 일치를 보장하지 않는다.

## 2026-07-01 — 공모전 일간 순위(DailyRank): 적재 시점 계산·저장 (다음 공모전 구현 시)

**상태:** 계획 — 다음 공모전에서 반영 (2025 공모전에는 소급 적용하지 않음)

**배경(현재 상태):** 공모전 소설의 저장 `Rank`는 **누적 View 기준**이다(`consolidate_contest_data.py`: View로 정렬 → `Rank = i+1`). 일간 view_change 순위는 **어디에도 저장되지 않으며**, view_change는 리스트 조회 시점(`get_contest_data_by_date`)에 즉석 계산될 뿐이다. `_rank_contest_items_by_view_change`(`main.py`)는 view_change 순위를 매기려던 **미완성 죽은 코드**다. 그 결과 상세 페이지에 **"일간 순위 추이"를 차트로 그릴 수 없다** — 순위는 상대값이라 특정 날 한 작품의 일간 순위를 알려면 그날 전체 작품의 view_change를 정렬해야 하는데, 단일 소설 trend 엔드포인트는 다른 작품 데이터에 접근하지 못하고 그 값이 저장돼 있지도 않다.

**결정:** 다음 공모전부터 일간 순위를 **조회 시점이 아니라 적재(consolidate) 시점에 계산해 DB에 저장**한다. 각 일자 항목에 `view_change`와 `DailyRank`(view_change 기준 순위)를 저장한다. 기존 누적-View `Rank`는 유지(둘 다 유용).

**구현 노트:**
- consolidate가 `CONTEST_AVAILABLE_DATES`에서 실제 직전 수집일을 찾아(메타 갱신 *전*이라 max 날짜 = 직전일) 그날 전체 작품 View를 로드(수천 건, 페이지네이션 1회 — 저렴).
- `view_change = View_D − View_직전일` → 정렬 → `DailyRank` 부여 → 각 항목에 저장.
- 첫 수집일: 직전일 없음 → view_change/DailyRank = null/New (원래 첫날은 일간 순위가 없음).
- 수집 공백: 캘린더 -1이 아니라 **실제 직전 수집일** 기준 (아래 "전날 계산" 항목과 동일 원칙).
- 상세 trend 엔드포인트는 저장된 `DailyRank`를 날짜별로 반환 → 차트가 일간 순위 추이를 직접 그림. 리스트 엔드포인트도 즉석 계산 대신 저장값 사용.
- 죽은 `_rank_contest_items_by_view_change`는 이 로직을 적재로 옮기며 삭제.
- (별도 결정 필요) 화면 헤드라인 "N위"를 누적-View `Rank` 대신 `DailyRank`로 바꿀지.

**왜 공모전에서만 정당한가:** 등록 공모전작 전수를 매일 추적하는 **닫힌·완전한 풀**이라 view_change 일간 랭킹에 누락 edge case가 없다(메인 사이트 일간 랭킹과의 대비는 아래 "일간 랭킹은 별도 파이프라인 대신…" 항목 참조). 적재 시 확정 저장하면 과거 순위가 **동결**돼 차트가 안정적이고 조회 시 전체 재계산이 사라진다.

**함께 볼 것:** 다음 공모전 셋업 시 태그 스코어링 신규 적용(아래 "공모전 태그 스코어링" 항목)과 함께 처리.

## 2026-07-01 — 일간 랭킹은 별도 파이프라인 대신 데일리 랭킹의 보조 컬럼으로

**결정:** 진짜 "일간 조회수 랭킹"을 위한 별도 파이프라인(전체 카탈로그 파싱 또는 다중 표면 후보 풀)은 **만들지 않는다.** 대신 기존 데일리 랭킹(주간 top-500 기반)에 **일간 조회수 변화량(view_change) 컬럼**을 보조 지표로 추가한다. 직전 수집일에 포착된 소설만 값을 표시하고(그 외 `New`), 정렬 가능하게 한다.

**이유:** 후보 풀을 아무리 여러 표면(주간/일간/장르/신작 등)에서 모아도 "모든 표면 컷오프 아래인데 일간 증분만 상위"인 edge case를 원천 배제할 수 없다. 단 하나의 누락 가능성이라도 있으면 **주 지표(authoritative ranking)로는 신뢰할 수 없고**, 그런 지표를 사실인 양 제공하는 것은 원치 않는 방향. 전체 30만+ 매일 파싱은 비용·서버 예의 면에서도 불가. 프로젝트 목적(트렌드 분석)에는 주간 랭킹의 안정성이 오히려 강점.

**영향:** view_change는 "주간 top-500 모집단 내 일간 무버"로만 해석해야 하며 전역 일간 top-N이 아니다. 신규 진입작은 delta 미정 → 숫자 대신 `New`(기존 `rank_change='New'`와 동일 패턴). 백엔드 `get_novels_by_date`는 이미 직전일 데이터를 조회하므로(순위변동 계산용) 추가 크롤링 없이 delta 산출 가능. **다중 표면 후보 풀 아이디어는 재현율 완전성 미달로 주 지표에 부적합 → 보류(재제안 방지를 위해 기록).**

**상태:** 유효

## 2026-07-01 — 데일리와 공모전의 "전날(previous date)" 계산을 다르게 유지

**결정:** 데일리 랭킹(`get_novels_by_date`, `get_novel_ranking_showcase`)은 **캘린더 -1일**로, 공모전(`get_contest_data_by_date`, `get_contest_showcase` → `_get_previous_contest_date`)은 **실제 직전 수집일**(available_dates 기반)로 previous date를 계산한다. 통일하지 않는다.

**이유:** 공모전의 핵심 가치는 노벨피아가 제공하지 않는 일간 랭킹을 `view_change`(직전 수집일 대비 조회수 증분)로 **직접 구성**하는 데 있다. 캘린더 -1일을 쓰면 수집 공백일에 "전날"이 없어 `view_change`가 누적 조회수 전체로 깨져 핵심 지표가 무너진다. 반면 데일리는 순위/순위변동만 쓰므로, 공백일에 전부 `rank_change='New'`로 나오는 게 오히려 정직하다 (2일 전과 비교한 가짜 하루 delta보다 낫다).

**영향:** 두 페이지의 공백일 동작이 의도적으로 다르다. `_get_previous_contest_date` / `_get_contest_available_dates_desc`는 살아있는 코드이니 제거 금지.

### 도메인 지식: 누적 View ≠ 랭킹·정산용 인증 조회수

작업하던 코딩 에이전트가 한 번 이 함정을 밟았다. 사용자가 도메인 지식으로 잡아냈다.

**영향:** `View` 차분을 지표로 쓸 거면 이름을 정직하게 붙여야 한다 —
"누적 조회수 증가량"이지 "일간 조회수"가 아니다(백로그 #15).

## 쇼케이스 카드: 표지 전면 + 글자 뒤 그라데이션 블러 (2026-08-30)

카드 구조가 세 번 바뀌었습니다. 현재가 최종입니다.

1. (구) 표지 전면 + 어두운 scrim으로 덮고 그 위에 흰 글자
2. (중간) 표지를 카드 위쪽에만 두고 글자는 그 아래 표면 위에
3. (현재) **표지 전면 + 글자 뒤에만 `backdrop-filter` 그라데이션 블러**

②는 글자가 항상 깨끗했지만 표지가 카드의 절반으로 줄었습니다. ③은 표지를 다시
전면으로 되돌리되 **어둡게 덮는 대신 흐리게** 합니다 — 표지 그림이 그대로 보이면서
글자도 읽힙니다. 글자 위치·크기·여백은 ②에서 잡은 값을 그대로 씁니다.

### 건드릴 때 주의

- **순위 칩은 `.media-rank-card__cover` 안에 있어야 합니다.** 하단 글자 띠(`__overlay`)가
  블러 레이어(`::before`)를 얹느라 `position: relative`이므로, 칩을 그 안에 두면 카드가
  아니라 띠를 기준으로 배치되어 제목 옆으로 내려옵니다. 소설 랭킹·공모전 두 곳 모두
  마크업에서 칩을 표지 안으로 옮겼습니다.
- **띠 안의 글자는 테마 토큰을 쓰면 안 됩니다.** 배경이 두 테마 모두 어두운 블러 띠라
  고정 밝은 값(`#f7f8fb`, `rgba(247,248,251,.82)`)을 씁니다. `--np-text-primary`를 쓰면
  라이트에서 어두운 글자가 되어 안 보입니다(`rank-move__to`가 실제로 그랬습니다).
- **띠는 글자 블록보다 5.5rem 위에서 시작하고, 어둡기와 블러 세기를 여러 단계로
  나눠 올립니다.** -2.4rem에 2스톱이었을 때는 글자 바로 위에서 블러가 갑자기 시작해
  가로줄이 그어진 것처럼 보였습니다. 배경 8스톱 + 마스크 5스톱입니다.
- **그라데이션 농도는 눈이 아니라 실측으로 잡았습니다.** 제목 구간 스톱이 0.34였을 때
  가장 밝은 표지에서 제목 대비가 3.79까지 떨어졌습니다. 현재 0.48/0.66으로 최저
  5.81입니다. 표지를 더 보이게 하려고 낮추려면 **반드시 밝은 표지 카드에서 픽셀 대비를

- **급상승의 이전/현재 순위는 알파 차이만으로 구분되지 않습니다.** 밝기(0.46 대 1.0),

### 대비 검사기의 한계 (이번에 또 걸렸습니다)

DOM을 거슬러 올라가며 배경을 찾는 방식은 이 카드에서 **전부 오탐**입니다 — 표지가

가상 요소라 아예 보이지 않습니다. 라이트에서 20건이 나왔지만 실제 픽셀로는 최저

## 표 정렬 (2026-08-30)

## 잔류율 산식을 업계 관행과 대조 (2026-08-30)

작가들이 중요하게 본다는 **연독률**과 우리 잔류율이 같은 것인지 조사했다. 결론부터:
**같지 않고, 같아지도록 바꾸지도 않는다.** 이유를 남긴다 — 이 근거가 없으면 나중에
누군가 "커뮤니티는 4화를 쓰는데 왜 1화지?"라며 되돌리려 할 것이다.

### 조사 결과 — 표준 산식은 존재하지 않는다

| | 세는 단위 | 분모 | 분자 | 위상 |
|---|---|---|---|---|
| **우리** | 표시 조회수 | 1번째 유효 회차 | 30번째 유효 회차 / 최신화 | 자체 파생 |
| 커뮤니티 연독률 | 표시 조회수 | **4화** | **(최신−3)화** | 관행 |
| 문피아 연독률 | 인증 조회수 | **비공개** | **비공개** | 공식(산식 미공개) |
| 노벨피아 독자지수 | **감상인원(사람 수)** | 1화 감상인원 | 1~N화 **누적** | 공식(상금 조건) |

- **문피아**는 연독률을 공모전 메뉴와 크리에이터 앱에 표기하지만 산식을 공개하지 않는다
  ("내부 기준에 따라 1시간마다 자동 집계", 20화·총 조회수 5천 이상만 표기).
  <https://nhelp.munpia.com/faq?faqCategoryId=379&page=2>
- **노벨피아**에는 '연독률'이라는 말이 없다. 대신 **독자지수**가 공식 지표로 있고
  신작챌린지 상금 지급 조건에 쓰인다. 이벤트 페이지 원문을 직접 확인했다:
  "독자 지수 계산 방식 (1화부터 특정회차 까지의 누적 감상인원) / (1화 감상인원)"
  <https://novelpia.com/event/2026_new_challenge>
  **감상인원(사람 수) 기반이라 우리는 재현할 수 없다** — 회차별 감상인원은 외부에 노출되지 않는다.
- 디시에 도는 다단계 공식(`T=(T1/T4)²/4×T1`)은 차원이 맞지 않아 **기각**했다.
  문피아 공식 산식으로 인용하면 안 된다.

### 우리 방식을 유지하는 이유

**1. 분모를 1화로 둔다 (커뮤니티는 4화)**
커뮤니티가 앞 3화를 자르는 이유는 "취향에 따라 탈락하는 독자"를 빼기 위해서다. 그러나
**노벨피아는 정액제라 유입도 쉽고 이탈도 쉽다.** 1화 이탈은 노이즈가 아니라 작품에 대한
신호다. 커뮤니티 기준이 문피아의 편당 결제 구조에서 나온 것이라 그대로 옮기면 오히려 틀린다.

**2. 30화 기준을 유지한다 (커뮤니티는 4화)**
노벨피아 무료분이 첫 15화이고, 그 두 배다. 문피아의 4화 기준과 다른 것이 정상이다.

**3. 최신화를 그대로 분자로 쓴다 (커뮤니티는 최신−3화)**
3화 오프셋은 "3화 ≈ 3일"을 가정한다. **연참(하루 여러 편 업로드)하면 3화 전이 3시간 전일
수 있어** 오히려 부정확해진다. 시간 기준으로 자르는 것이 정공법이지만 회차 게시일 저장 =
파이프라인 변경이라 지금은 하지 않는다.

**4. 커뮤니티식으로 갈아타도 문제가 해결되지 않는다** — 아래 실측 참고.

### 실측: 세 방식 모두 회차 수 편향이 있다 (2026-08-29, n=370)

회차 수와의 스피어만 상관 (0에 가까울수록 길이 중립):

| 방식 | 상관 | 성격 |
|---|---|---|
| 우리 최신 잔류 (고정 30화 창) | **+0.70** | 길수록 유리 |
| 전 구간 비율 (커뮤니티식과 같은 성격) | **−0.64** | 길수록 불리 |
| 회차당 평균 유지율 (기하평균) | **+0.96** | 값이 93~99%에 뭉쳐 증폭 |

구간별 중앙값 (~50화 → 700화~): 우리 20.2%→70.6% / 전 구간 14.8%→2.0% / 기하 93.67%→99.60%.

**커뮤니티식이 이 문제를 안 겪는 이유는 산식이 좋아서가 아니라 용도가 다르기 때문이다.**
인용된 벤치마크에는 전제가 붙어 있다 — "22~36화 구간, 투베 진입작 한정, 최소 15~20화 이상".
비슷한 길이끼리만 비교하는 도구다. 우리는 16화~1137화를 한 표에 놓고 정렬까지 시키므로
애초에 그 용도가 아니다. **갈아타면 편향의 방향만 뒤집힌다.**

### 알려진 한계 (고치지 말고 알고 있을 것)

- **표시 조회수는 계속 자란다.** 6일간 328건 **전부(100%)** 1화 조회수가 증가했다
  (중앙 +1.18%, 최대 +345%). 즉 분모는 "1화를 본 사람 수"가 아니라 누적 조회수다.
  노벨피아도 "표면적으로 드러나 있는 조회수와 차이가 생길 수 있습니다"라고 공식 인정한다.
  <https://novelpia.com/faq/all/view_382970/>
  → **"잔류"가 함의하는 "같은 사람이 계속 읽는 비율"을 우리 값은 보장하지 못한다.**
- **최신화는 아직 덜 찬다.** 새로 올라온 회차를 3일차→6일차로 추적한 결과 7건 전부
  10% 이상 더 찼다(중앙 +14.3%, 최대 +17.7%). 편차가 좁아 한 방향으로 완만하게 걸리는
  편향이라 값을 못 쓸 정도는 아니지만, 자주 연재하는 작품이 불리하다.
- **"역순 30번째"의 위치가 작품마다 다르다.** 작품 전체에서 중앙 84% 지점이지만
  최소 6% ~ 최대 99%다. 43화 작품에선 앞부분을, 1000화 작품에선 거의 끝을 잰다.
- **우리 "1화"의 35.7%는 실제로 0화(프롤로그)다.** 프롤로그는 유입이 가장 부풀어 있는
  회차라 그 작품들은 분모가 한 번 더 부푼다.
- **화면의 회차 수(`Eps`)와 우리가 "최신화"로 쓴 회차 번호는 50.5%만 일치한다.**
  공지·외전을 걸러 세기 때문이다. 사용자가 대조하면 어긋나 보인다.
- **여성향(로판·BL) 벤치마크는 자료를 한 건도 찾지 못했다.** 확인된 수치가 전부 문피아
  남성향이라, 기준표를 화면에 옮기면 편향이 실린다.

### 화면 표기 원칙

**돌아다니는 연독률 기준표(80% 대박 / 40% 이하 위험)를 우리 숫자에 대면 안 된다.**
그 기준은 4화를 분모로 재고 우리는 1화를 쓰므로 구조적으로 더 낮게 나온다.
'연독률'이라는 말을 화면에 쓰지 않고 '초반 잔류'·'최신 잔류'로 부르는 현재 표기를 유지한다.

## 30화 미만이면 초반 잔류를 계산하지 않는다 (2026-08-30)

**변경:** `_compute_retention_rates()`에서 유효 회차 30개 미만일 때의 대체 계산
(`최신화 / 1화`)을 제거했다. 이제 `EarlyRetentionRate = None`이다.

**이유:** 대체 계산은 게이트가 아니라 **아무 표시 없이 다른 정의의 값으로 바꿔치기**하는
것이었다. 두 가지가 문제였다 —

1. 정렬하면 서로 다른 정의의 값이 한 열에 섞인다.
2. 초반 잔류와 최신 잔류가 **최신화 조회수를 분자로 공유**하게 되어, 아직 덜 찬 최신화의
   왜곡이 두 숫자에 동시에 실린다.

문피아도 20화·5천 조회수 미만이면 정의를 바꾸지 않고 **미표기**한다.

**영향:** 초반 잔류 산출이 370건 → 338건(91.4%)으로 줄었다. 최신 잔류는 변화 없다
(30화 미만 작품은 "역순 30번째"가 없어 원래도 `None`이었다 — 즉 이전에는 같은 행에서
초반만 값이 있고 최신은 비어 있는 상태였다).

**프론트는 고칠 것이 없다.** `formatPercent()`가 `null`을 `-`로 그리고, 정렬은
`aValue === null → return 1`로 항상 뒤로 민다. 실제 화면에서 30화 미만 18건이
초반·최신 모두 `-`로 표시되는 것을 확인했다.

**배포:** 백엔드 Lambda 재배포 필요(자동 배포 없음). 크롤러·프론트 변경 없음.


## 태그 지형 지도의 범례를 축 설명만 남긴다 (2026-08-30)

범례가 '읽는 법 / 표시 규칙' 두 문단이었는데, 정작 **축이 무엇인지가 문단 속에 묻혀
있었다.** 지도를 볼 때 필요한 건 축 두 개와 원 크기뿐이다. 한 줄씩 늘어놓는 목록으로 바꿨다.

- **가로** 그 태그를 단 작품이 몇 개인지
- **세로** 그중 상위 100위에 얼마나 몰렸는지 (1.0이면 순위와 무관)
- **원 크기** 인기 점수
- **이름** 눈에 띄는 태그에만. 나머지는 원에 커서를 올리면 나옵니다

**뺀 것과 옮긴 곳**

- *주류 기준 N작품(상위 25%)* — 세로 점선의 의미. 4분면 이름이 이미 네 구석에 있어
  점선이 무엇을 가르는지 따로 설명할 필요가 없다.
- *집중도 8 초과는 ▲로 축 상단 고정* — 삼각형이 몇 개 안 되고, 그 태그는 호버하면
  실제 값이 나온다.
- *등장 5작품 미만 N개 제외* — **지도 헤더의 '태그 74개' 옆으로 옮겼다.** 개수를
  말하는 자리에 제외 개수가 함께 있는 편이 맞다.

**이름이 붙는 원과 안 붙는 원의 차이는 규칙이 있다** — 인기 점수 순위와 집중도 순위를
정규화해 더한 값의 상위 18개다(`labelPriority`). 자리가 겹치면 건너뛴다. 이 규칙을
화면에 그대로 쓰면 길어지므로 "눈에 띄는 태그에만"으로 줄이고, **나머지는 호버로 볼 수
있다는 점을 함께 적었다.** 규칙 자체를 바꾸지는 않았다.

**그 밖에**

- 집중도 값이 `1.2×`로만 떠 있어 무슨 수치인지 알 수 없었다. 요약 카드와 구역 목록 칩
  모두 `집중도 1.2×`로 이름을 붙였다(툴팁에는 이미 있었다).
- 세로축 이름('↑ 상위권 집중도')이 지도에 붙어 있어 차트 위 여백을 24→40px,
  라벨 오프셋을 -6→-22로 늘렸다.


## 선택 패널 간격과 차트 포커스 링 (2026-08-30)

**선택한 태그 패널이 위 요소에 딱 붙어 있던 이유** — `.tag-rankings-page .selected-tag-panel`이
`height: 100%; margin-top: 0`을 갖고 있었다. 패널이 그리드 칸 안에 있던 시절의 잔재인데,
지금은 페이지 셸의 직계 자식이라 `margin-top: 0`(특이도 0,2,0)이 페이지의 간격 규칙
`.tag-rankings-page > * + *`(0,1,0)을 이기고 있었다. 둘 다 제거했다.

**차트를 클릭하면 흰 테두리가 생기던 이유** — Recharts가 접근성을 위해 SVG
(`.recharts-surface`)에 `tabindex="0"`을 붙인다. 그래서 클릭하면 **브라우저 기본
포커스 링**이 그려지고, 다크 테마에서는 그게 흰 선으로 보인다.

`outline: none`으로 지우면 키보드 사용자가 차트에 포커스가 갔는지 알 수 없으므로,
`:focus`는 지우고 `:focus-visible`에만 토큰 색 링을 남겼다. 이 규칙은 특정 페이지가
아니라 `components.css`에 두었다 — 같은 문제가 소설 상세·트렌드 등 Recharts를 쓰는
모든 화면에 있기 때문이다.


## 화면 채우기는 .app-shell 하나만 책임진다 (2026-08-30)

**증상:** 특정 뷰포트 **높이 경계**에서 화면이 빠르게 깜빡였다. 개발자 도구를 연
상태에서 잘 보였는데, 도구 자체가 원인이 아니라 **도구가 뷰포트 높이를 그 경계로
밀어넣기 때문**이었다(아래쪽 패널 크기를 끌면 경계에서 발생).

**원인:** `min-height: 100dvh`가 **body · #root · .app-shell 3중으로** 쌓여 있었고,
`.app-main`이 다시 `calc(100dvh - 64px)`에 하단 패딩까지 더했다. 그 결과 내용과
무관하게 **페이지가 항상 뷰포트보다 62px 길었다**(실측: 모든 높이에서
`scrollHeight = vh + 62`).

세 가지가 따라온다 — (a) 내용이 짧은 페이지에도 항상 세로 스크롤바가 있었고,
(b) 뷰포트 높이가 바뀔 때마다 4단계가 전부 다시 계산됐으며, (c) '자연 콘텐츠 높이'와
'dvh로 정해지는 높이'가 교차하는 지점에서 레이아웃이 두 값 사이를 오갔다.
`dvh`는 이름 그대로 **동적**이라 뷰포트가 변하는 동안 계속 재계산된다.

**수정:** `.app-shell`만 `min-height: 100dvh`를 갖고 `display: flex; flex-direction: column`,
`.app-main`은 `flex: 1 0 auto`로 남는 공간을 채운다. dvh 계산이 사라졌다.
body·#root의 중복 `min-height`도 제거했다.

**검증:** 수정 전 모든 높이에서 `scrollHeight = vh + 62`(스크롤바 상시).
수정 후 콘텐츠보다 뷰포트가 크면 `scrollHeight = vh`이고 **스크롤바가 사라진다**
(clientWidth 1265 → 1280). 교차점(vh 1209) 앞뒤 2px 간격으로 훑어도 진동 없음.

**새 페이지를 만들 때 `min-height: 100dvh`나 `calc(100dvh - ...)`를 또 쓰지 마세요.**
셸이 이미 화면을 채우므로 중첩되면 같은 증상이 돌아옵니다.

## 앱 헤더에서 backdrop-filter 제거 (2026-08-30)

**맥락:** 위 깜빡임을 조사하다 먼저 발견한 별개의 문제다. 이것만으로는 증상이
해결되지 않았지만(원인은 위의 dvh 중첩), 그 자체로 고쳐야 할 것이었다.

**원인:** `.app-header`가 `position: sticky; top: 0`인데 `backdrop-filter: blur(20px)`를
함께 걸고 있었다. sticky 요소에 backdrop-filter가 있으면 스크롤·레이아웃 변화마다
뒤 배경을 다시 블러해야 해서 리페인트 비용이 크고, 개발자 도구처럼 렌더링 부하가
늘어난 상태에서 그 비용이 눈에 보이는 깜빡임으로 나타난다.

**이미 금지돼 있던 조합이다.** CLAUDE.md에 "iOS Safari: sticky `top:0` 헤더에
`backdrop-filter` 금지(상태바 색상 lock-in 버그)"로 적혀 있었는데 코드가 그걸 어기고
있었다. iOS 버그와 데스크톱 리페인트 비용이 같은 원인에서 나온 것이다.

**수정:** 배경을 `var(--np-canvas-elevated)` 불투명으로 바꾸고 backdrop-filter를 지웠다.
지금 테마는 유리질감을 쓰지 않으므로 불투명이 오히려 일관된다.

**조사 과정에서 배제한 것들** (같은 증상을 다시 보면 이건 다시 안 봐도 된다) —
콘솔 오류 0건, DOM 변경 0건/5초(무한 리렌더 아님), 폭 9종에서 레이아웃 진동 없음
(`auto-fit + minmax` 스크롤바 토글 아님), 실행 중인 CSS 애니메이션 0개.

표지 칩 등에 남은 backdrop-filter는 sticky가 아니라 그대로 둔다 — 문제는
'blur' 자체가 아니라 '스크롤을 따라다니는 요소에 건 blur'다.


## 영문 눈썹 라벨 + 큰 값 카드 패턴 제거 (2026-08-30)

`LIVE MODULE` / `PRIMARY LENS` / `DATA SOURCE` 같은 **영문 대문자 라벨 아래에 큰 글자로
값을 얹은 카드**를 전 페이지에서 걷어냈다. 사용자가 "너무 AI가 만든 디자인 같다"고

숫자처럼 보이는 자리에 숫자가 아닌 것을 넣으면 화면이 채워진 것처럼 보일 뿐이다.

**지운 것**

- `InsightStrip` 컴포넌트와 CSS 전부 삭제. 쓰이던 4개 페이지(데이터 분석·태그 트렌드·
  소설 트렌드·공모전 태그)에서 제거했다. 남겨두면 다시 쓰인다.

- `PageHero`의 영문 eyebrow: `Discovery Desk` / `Trend Lens` / `Trend Lab` /
  `Contest Tag Atlas` — 전부 제거. 제목이 이미 한국어로 무엇인지 말한다.
- 태그 트렌드 히어로의 큰 값 카드 두 장. 기간은 바로 아래 '기간 선택' 패널에 이미 있었다.

**한국어로 바꾼 것**

- 카테고리 라벨 `Trend Leader` / `Broad Popular` / `Efficient Niche` / `Cooling Down`
  → 아래 섹션 제목과 같은 `트렌드 주도` / `대중적 보편` / `고효율 틈새` / `하락세`.
  같은 것을 두 이름으로 부르고 있었다.
- 빈 상태 `No Result` / `No Tags` / `Analysis Error` → 한국어.

**데이터 분석 페이지는 링크 두 개만 남겼다.** 담을 분석은 따로 설계 중이고,
그게 들어오기 전까지 빈 카드로 자리를 채우지 않는다.

**새 화면을 만들 때** — 영문 눈썹 라벨을 붙이지 말고, 값 자리에 값이 아닌 설명을
넣지 마세요. 보여줄 숫자가 없으면 그 카드는 필요 없는 카드입니다.

## 쇼케이스 두 칩의 강조 수준을 맞춘다 (2026-08-30)

'급상승 5작품'의 상승 칩만 **색 테두리 + 색 글자 + 틴트 배경**으로 3중 강조를 받고,
'상위 5작품'의 순위 칩은 전부 무채색이었다. 그래서 정작 주인공인 상위권보다

대비 5.75로, 상승 칩 6.50과 비슷한 수준이다. 값을 바꾸려면 밝은 표지·어두운 표지
양극단에서 다시 재세요.


## 페이지 설명문은 사용자에게 하는 말로 쓴다 (2026-08-30)

제목 아래 설명이 **페이지를 가리키는 말**이었지 사용자에게 하는 설명이 아니었다.
"랭킹 데이터를 기간과 묶음으로 다시 보는 화면", "사용량과 상위권 집중도로 읽는 태그 지형"
처럼 명사를 나열해 놓으면 읽는 사람은 여기서 뭘 할 수 있는지 알 수 없다.

**세 가지를 기준으로 전부 다시 썼다.**

1. 명사 나열이 아니라 문장으로 — "날짜별 인기 순위와 전일 대비 변동" →
   "매일 밤 9시에 기록한 노벨피아 인기 순위입니다. 날짜를 바꾸면 그날의 순위를 볼 수 있습니다."
2. 전문어를 일상어로 — `사용량`·`상위권 집중도`·`포지셔닝` 같은 말을 화면에서 뺐다.
3. 시각을 사람 말로 — `21시` → `밤 9시`, `오후 2시 집계` → `오후 2시에 기록합니다`.

**소설 트렌드는 본문까지 고쳤다.** "레이아웃과 테마는 미리 정비했고, 실제 분석 지표는
다음 단계에서 연결할 수 있습니다"라는 **개발자에게 하는 말이 사용자 화면에 그대로**
나가 있었다. 준비 중이라는 말만 하고 끝내면 사용자는 빈손으로 나가므로,
지금 할 수 있는 것(소설 랭킹에서 작품을 누르면 그 작품의 추이를 볼 수 있다)을 알려준다.

`EmptyState`의 눈썹 라벨 `결과 없음`은 옵션으로 바꿨다. 검색·필터 결과가 비었을 때는
맞는 말이지만, 아직 만들지 않은 화면에서는 뜻이 다르다.

## .panel-card 컨테이너와 헤더 규칙을 합치지 말 것 (2026-08-30)

`.panel-card`(컨테이너)와 `.panel-card__header`(헤더)가 한 셀렉터 목록으로 합쳐져
있어서, 컨테이너에 헤더 스타일(가로 플렉스 + 아래 테두리 + 헤더 배경)이 걸렸다.
그 결과 **제목과 본문이 좌우로 나란히 놓이고 패널 모서리(radius)가 전부 사라졌다.**
`/tags/rankings`와 `/trends/novels`에서 눈에 띄게 깨졌다.

원인은 내가 `.trend-card` 규칙을 지우면서 쓴 정규식 `^\.trend-card[^{]*\{[^}]*\}`이
`[^{]*`로 줄바꿈까지 건너뛰어 **뒤따르던 셀렉터 목록과 그 규칙 본문까지 함께** 지운
것이다. 여러 셀렉터가 한 목록에 묶인 CSS에서 클래스 하나만 지울 때는 셀렉터 줄만
지워야 하고, 규칙 전체를 매칭하는 정규식을 쓰면 안 된다.

컨테이너 그룹(`.panel-card` `.data-table-shell` `.ranking-module` `.spotlight-card`
`.featured-tag-card`)과 헤더 그룹(`__header` 셋)은 **반드시 분리해 둔다.**


## 태그 트렌드를 '기간 동안의 변화'로 재구성 (2026-08-30)

**바꾼 이유 둘.**

1. 보여주던 수치가 `기울기 +0.051`, `로컬 리프트`, `평균 총합 점수`였다. 독자·작가가
   "이게 좋은 건가"에 답할 수 없는 값이고, 태그 랭킹이 쓰는 말(작품 수 / 집중도 /
   인기 점수)과도 달라 같은 대상을 두 언어로 설명하고 있었다.
2. 백엔드 4분류(trend_leader / broad_popular / efficient_niche / declining)가
   태그 랭킹의 4분면과 하는 일이 겹쳤다. **태그 랭킹이 '오늘의 지형'을 맡으므로
   여기는 '기간 동안의 변화'만 맡는다.**

### 새 구조

`뜬 태그` / `식은 태그` / `새로 들어온 태그` / `사라진 태그`.
'뜬·식은'은 태그 랭킹에 이미 있는 말이라 어휘가 통일된다.

수치는 전부 태그 랭킹과 같은 말로, 변화를 `→`로 보여준다.

### 5작품 하한이 반드시 필요하다 (실측)

30일 비교에서 **하한 없이 순위 변동으로 줄세우면 상위가 전부 1~2작품짜리로 찬다.**

| 하한 | 남는 태그 | 순위변동 범위 |
|---|---|---|
| 없음 | 145개 | +93 ~ −73 (1위가 '1작품→7작품') |
| 5작품 | 65개 | +19 ~ −20 |
| 10작품 | 46개 | +6 ~ −14 |

꼬리가 촘촘해서 작품 하나가 늘면 수십 계단이 움직인다. 하한을 빼면 트렌드가 아니라
노이즈를 보여주게 된다. 태그 랭킹의 집중도 산출 하한과 같은 값이다.

### 정렬 기준은 화면에 보이는 값이어야 한다

한때 인기 점수 변화율(%)로 정렬했다. 판별력은 그쪽이 좋지만 — `+115%` 한 줄만
칩에 띄워 놓으니 **무엇이 115% 늘었는지 알 수 없었다.** 칩을 순위 변동으로 바꾼 이상
정렬도 순위 변동으로 간다. 목록이 왜 그 순서인지 화면에서 읽히지 않으면 정렬 기준이
아무리 좋아도 소용없다.

```
정렬:  b.rankChange - a.rankChange  ||  b.scoreChange - a.scoreChange   (동점만 %로)
칩:    영지   61위 → 53위 · 7→10작품
패널:  순위 61위→53위 / 등장 7→10작품 / 인기 점수 1.2 → 1.8 (+43%) / 집중도
```

%는 없애지 않고 **이름을 붙여** 패널로 내렸다. `인기 점수 1.2 → 1.8 (+43%)`은 라벨이
있으니 읽힌다.

**새로 들어온·사라진 태그도 작품 수만으로 끝내지 않는다.** `10작품 · 44위`처럼 순위를
같이 준다. 사라진 쪽은 `27위였음`으로 시제를 붙여 지금 값이 아님을 표시한다.

### 데이터 수집 방식 — 기간 전체를 한 번에

**표본을 뽑지 않는다.** 기간이 정해졌으면 그 기간의 수집일을 전부 계산에 넣는다.
한때 균등 8개를 뽑아 순차 호출했는데, 7일을 골라도 8일을 뽑는 꼴이었고 30일을 고르면
22일치가 버려졌다. 트렌드 화면에서 데이터를 버리는 건 그 자체로 답이 안 된다.

그래서 백엔드에 배치 엔드포인트를 뒀다:

`GET /api/trends/tags/series/{start_date}/{end_date}`
→ `{dates: [...], tags: {태그: {rank: [], count: [], score: [], lift: []}}}`

DynamoDB `batch_get_item`으로 **100키씩** 묶어 가져오고, 날짜마다
`_tag_stats_without_blocked`를 적용한 뒤 power_score 내림차순으로 순위를 매긴다.
상한은 180일.

| 방식 | 7일 | 비고 |
|---|---|---|
| 날짜별 `get_item` 병렬 8개 | 21.7초 | 백엔드가 단일 워커라 서로 막는다 |
| 날짜별 `get_item` 순차 8개 | 3.2초 | |
| **`batch_get_item` 배치 1회** | **1.04초 / 61KB** | 30일도 3.16초 / 243KB |

기본 기간은 **7일**.

이 응답으로 **태그별 시계열이 같이 온다.** 태그를 고르면 기간 동안의 순위 추이를
차트로 보여준다(순위 축은 뒤집어 위로 갈수록 상위). 예전에는 백엔드 4분류 API의
`score_series`에 의존했는데, 그건 4묶음에 든 80개 태그만, 인기 점수 하나만 줬다.
지금은 모든 태그가 대상이고 순위·작품 수·집중도까지 함께 본다.

### 그 밖에

- **기간 선택 패널을 없앴다.** '기간 선택'이라는 제목과 "기간을 바꾸면 모든 카테고리
  카드가 같은 기준으로 다시 계산됩니다"라는 설명을 단 패널로 감싸져 있었는데,
  시작·종료 입력이 이미 무엇인지 말하고 있었다.
- **카드 형식을 태그 랭킹과 통일했다**(`tag-zone-chip`). 두 페이지가 같은 태그를
  다른 모양으로 보여줄 이유가 없다.
- 백엔드 `/api/trends/tags/analysis` 는 이제 프론트에서 쓰지 않는다. 지우지는 않았다.
- **날짜 아래 파란 점 표시를 껐다**(`showNovelDataIndicator={false}`). 그 점은 '이 날짜에
  소설 데이터가 있다'는 뜻인데 여기서는 태그를 본다. `DateRangePicker` 자체는 그대로
  둬서 소설 상세는 계속 점을 쓴다.


## 태그 랭킹 선택 패널은 '오늘'이 아니라 '추이'를 맡는다 (2026-08-30)

지도에서 원을 클릭하면 **같은 내용이 두 군데에 떴다.** 툴팁이
`등장 12작품 · 집중도 8.0× / 인기 점수 3.46 · 변동 +3`을 보여주는데, 위의 선택 패널이
같은 값 넷을 그대로 다시 보여줬다. 패널을 열어 봐야 새로 아는 게 없었다.

### 한 화면에 시간 기준을 둘 두지 않는다

처음 고칠 때는 패널의 `순위`·`등장`만 14일 비교로 바꾸고 `집중도`·`인기 점수`는
"지도의 두 축이니까" 오늘 값으로 남겼다. **이게 더 나빴다** — 한 줄 안에 기준이 둘이
섞였는데 어느 쪽도 라벨이 없어서, 14일 차트 위의 `45위 → 34위`가 무슨 기준인지
알 수 없었다. 사용자 지적: "그래프는 14일치인데 그 위의 전후 비교 수치는 14일 기준이
아니잖아."

역할을 **시간 축으로** 완전히 갈랐다.

| | 맡는 구간 | 보여주는 것 |
|---|---|---|
| 툴팁(hover) | **오늘** | `1위 · 어제와 같음` / 등장·집중도·인기 점수 |
| 선택 패널(click) | **최근 14일** | 네 수치 전부 `시작 → 끝` + 순위 추이 차트 |

태그 랭킹은 '오늘의 지형'을 보는 페이지이므로 **원 옆(툴팁)은 오늘과 직전 대비**를,
**위쪽 박스(패널)는 기간 전체**를 맡는다. 각자 다른 질문에 답하므로 중복이 아니다.

패널 맨 위에 구간을 적는다(`8.17 → 8.30 · 수집일 14일`). **'14일'이라고 쓰지 않고
응답이 준 실제 첫·끝 날짜를 쓴다** — 수집이 빠진 날이 있으면 14일이 아니기 때문이다.

패널의 색 띠도 14일 변동을 따르게 바꿨다. 예전엔 어제 변동으로 칠했는데, 그러면
초록 띠 아래에 14일 하락이 적히는 경우가 생긴다.

### `-` 하나로 '변동 없음'과 '데이터 없음'을 뭉뚱그리지 않는다

`formatRankChange`가 `0`과 `null`을 똑같이 `-`로 돌려줘서, 1위 태그가
`어제 대비 -`로 보였다. 움직이지 않은 건지 비교할 데이터가 없는 건지 알 수 없다.
구절 전체를 만들게 바꿨다:

| rank_change | 표시 |
|---|---|
| `0` | `어제와 같음` |
| `+3` / `−1` | `어제보다 ▲3` / `어제보다 ▼1` |
| `'New'` | `오늘 처음` |
| `null` | **구절 자체를 뺀다** (`1위`만) |

**차트는 태그 트렌드와 같은 컴포넌트다**(`components/tag/TagRankChart`). 두 페이지가
같은 태그의 같은 그림을 다르게 그릴 이유가 없다.

### 호출은 태그를 처음 고를 때 한 번뿐

`/api/trends/tags/series` 응답에 **그 기간의 모든 태그**가 들어 있으므로, 첫 선택 때
14일치를 한 번 받아 두면 이후 어떤 태그를 눌러도 추가 호출이 없다(`api.ts` 5분 캐시).
날짜를 바꾸면 캐시 키가 달라져 다시 받는다.

추이는 부가 정보라 **실패해도 조용히 넘어간다** — 받아 오기 전이거나 그날 없던 태그면
패널은 오늘 값만 보여주고 차트를 빼며, 에러 배너를 띄우지 않는다. 지도와 목록은
추이와 무관하게 이미 그려져 있다.

### 자리는 브리핑 아래, 지도 위

독자·작가·IA·최소변경 네 관점으로 독립 설계안을 받았는데 **넷 다 같은 자리를 골랐다.**
이름이 '랭킹'인 페이지는 첫 화면에 1위가 있어야 하고, 지도는 그 다음 '왜 그런가'를 맡는다.

### 표 규격

`순위 · 변동 · 태그 · 작품 수 · 상위권 집중도 · 인기 점수` — 태그 이름을 변동 바로 뒤에
둔다. 소설 랭킹 표(`순위/변동/제목/작가/…`)와 같은 순서다. 숫자를 먼저 읽고 나중에
무슨 태그인지 아는 건 순서가 거꾸로다.

- **집중도가 없는 태그도 전부 넣는다.** 지도·존 카드는 집중도(5작품 이상)가 있어야
  성립하지만 '랭킹'은 그렇지 않다. 77개가 아니라 183개 전부다.
- **값이 없는 칸은 정렬 방향과 무관하게 항상 뒤로.** 집중도 내림차순을 눌렀는데
  집중도 없는 태그가 맨 위를 차지하면 표가 쓸모없어진다.
- `'New'`는 수치가 아니므로 변동 정렬에서 뺀다.
- 태그 열에 남는 폭을 전부 주면 이름과 숫자 사이가 화면 절반만큼 벌어져
  "이 8.0×가 어느 태그였지" 하고 눈이 되짚게 된다. `table-layout: fixed`로 폭을 나눈다.
- 행을 누르면 위쪽 선택 패널이 열린다 — 지도의 원을 누르는 것과 같은 동작이다.

390px에서 **값은 여섯 열이 다 들어가는데 헤더만 넘쳐서** 옆 칸과 겹쳤다
(`상위권 집중도` + `인기 점수` → `집중띭기 점수`). 가로 스크롤이 붙은 순위표는 훑기가
어려우므로, 좁은 화면에서만 짧은 라벨로 바꾸고(`집중도`/`점수`/`작품`) 여백을 줄였다.

**앱 문제가 아니다** — `body { overflow-x: clip }` 을 `visible` 로 바꿔 A/B 했는데
결과가 같았다. 스크롤이 걸린 동작은 실제 브라우저에서 확인해야 한다.

표를 더한 지금, 이 페이지는 태그를 **다섯 방식**으로 보여준다: 브리핑 4장 / 순위표 /

## 데이터 분석 페이지를 단일 리포트로 만든다 (2026-08-31)

허브가 아니라 **페이지 자체에 내용**을 넣는다. 맨 위 기간 선택 하나(최근 7/30/90일)가
아래 모든 섹션을 지배하는 한 장짜리 리포트다. 이전 판은 링크 한 개짜리 허브였고,
그 앞은 영문 눈썹 라벨에 "모듈 허브" 같은 값을 얹은 카드가 줄지어 있어 숫자처럼 보이는
자리에 숫자가 하나도 없었다.

**역할은 '작품 단위 기간 축'.** 소설 랭킹=오늘 하루, 태그 랭킹=오늘의 태그,
태그 트렌드=기간별 태그, 소설 상세=작품 하나를 이미 맡으므로 그 사이 빈 칸만 맡는다.

**마운트 시 스냅샷 2~6개를 받아 8개 섹션 전부가 재사용한다.** 섹션마다 따로 fetch 하지
않고 백엔드 변경도 없다. 순차로 받는다 — 백엔드가 단일 워커라 병렬이 더 느리다.

### 프리셋은 캘린더가 아니라 '최근 N개 수집일'

`dates.slice(0, N)`. 캘린더로 30일을 자르면 수집이 없던 날까지 세어 실제 표본이 줄어든다.
7일→2개, 30일→4개, 90일→6개 스냅샷을 균등 간격으로 뽑되 양 끝은 반드시 포함한다.

### 신규 진입 판정에 `rank_change` 를 쓰지 않는다

백엔드의 이전 날짜가 캘린더 −1일이라 **결손일 다음 날은 전 작품이 `'New'` 로 튄다.**
ID 집합 차집합(`end − start`)은 그 영향을 아예 받지 않는다.

### 한 번 폐기했던 4개 섹션을 되살렸다

심사에서 reject 됐던 것들인데, 사용자가 "보고 판단하겠다"고 해 전부 구현했다.
reject 사유는 그대로 유효하므로 **함정을 감추는 대신 화면에 드러냈다**:

| 섹션 | 원래 reject 사유 | 살리면서 한 처리 |
|---|---|---|
| 초반·최신 잔류 (구 '정주행 안전도') | 최신 잔류는 연재가 멈춘 작품일수록 높다 | **연재 페이스와 교차**해 회차가 늘지 않은 작품에 경고 배지 |
| 같은 순위대와 견주기 (구 '체급 진단') | 전체 백분위는 순위가 곧 답이 됨 | 전체가 아니라 **같은 순위 구간 안**에서만 백분위 |
| 신규 진입 생존 곡선 | 상위 300→500 변경으로 코호트 비교 불가 | 창이 2025-07-20을 넘으면 **경고 배너** |
| 태그 조합 | 기간 축과 무관 | 빈도가 아니라 **lift**(각자 흔한 정도 대비 배수)로 정렬 |

### 실측으로 정한 상수

- **추천비 눈금은 상수로 박는다**(0.045 / 0.055 / 0.078 / 0.095). 2025년 세 날짜가
  중앙 0.061~0.065·p90 0.093 이었는데 1년 넘은 2026-08-31이 중앙 0.0664·p90 0.0948로
  거의 그대로였다. 날짜마다 눈금이 흔들리지 않는 쪽이 비교에 낫다. 분기마다 재확인.
- **`View < 50,000` 하한 유지.** 364편 중 17편(4.7%)만 걸리고 그중 최고 순위가 217위다.
- **회차 감소('측정 불가')는 사실상 없다.** 8/24→8/31 양쪽 등장 317편 중 0편.
  그래도 0으로 뭉개지 않고 따로 분류한다 — 회차 통합·삭제를 '연재 안 함'으로
  적으면 사실이 아니다.

### 구현하며 잡은 것

- **리드 문장의 분모와 분자가 어긋났다.** "지금 목록에 있는 364편 가운데 68편"이라고
  써 놓고 68은 `pace` 맵 전체(이미 목록을 떠난 작품 포함)를 센 값이었다. 섹션 표는
  57편이라 화면 안에서 숫자가 안 맞았다. 분자도 `end.rows` 기준으로 바꿨다.
- **추천비 두 목록이 완전히 같았다.** '전체 상위'와 '100위 밖'을 나란히 뒀는데 추천비
  상위 12편이 전부 100위 밖이라 같은 카드가 두 번 나왔다. **순위로 갈랐다**(100위 안 / 밖).
- **신규 진입 태그 막대가 전부 '2편 · 3.5배'였다.** 신규 100편일 때 2편짜리 태그는
  배수만 크고 뜻이 없다. 하한을 `max(4, 신규의 4%)` 로 두고, **막대 길이를 정렬 기준과
  같은 값(배수)** 으로 그렸다 — share 로 그렸더니 전부 5% 미만이라 여덟 개가 똑같이 비었다.
- **추천비 눈금 3칸의 글자 대비가 2.69였다.** 부모의 보조색을 물려받는데 배경 농도가
  짙어져서다. 칸마다 글자색을 명시했다.
- **Recharts 범례 글자색이 선 색과 같게 인라인으로 박힌다.** 라이트에서 `--np-chart-2`가
  흰 배경 위 3.57로 미달했다. 색 구분은 옆 선 표식이 하므로 글자는 보조색으로 되돌렸다.

### 함정: `recharts_measurement_span` 은 대비 검사 오탐

Recharts 가 `<body>` 직속에 두는 텍스트 측정용 `<span>0</span>` 이다. 화면 밖에 있는데
`offsetParent` 가 있어서 가시성 검사를 통과한다. 대비 검사에서 `id` 로 제외해야 한다.


## 2026-09-05 — ETL → ELT: 원본 HTML을 남긴다

**결정:** 크롤러가 받은 HTML 원본을 S3에 남기고, 파싱은 그 위에서 다시 돌릴 수 있게 한다.

**이유:** 기존 구조는 크롤러가 HTML을 파싱해 24개 컬럼 CSV로 만들고 HTML을 그 자리에서
버렸다. `CSV_HEADERS`에 없는 필드는 `extrasaction='ignore'` 때문에 **에러도 없이**
사라졌고, 새 필드를 알게 되어도 과거를 채울 방법이 없었다. 이 리포에는 그 필요가 실제로
두 번 있었다 — 성인 배지를 `span.b_19`로 넓혀 회차 배지까지 잡은 일, 정규식으로 HTML을
훑어 `<script>` 안 템플릿 때문에 일반작을 전부 오판한 일. 원본이 있었으면 둘 다
소급해서 고칠 수 있었다.

**단, 소급의 한계:** 원본이 없던 과거는 되살릴 수 없다. 재크롤링은 *오늘의* 페이지를
줄 뿐 그날의 상태가 아니다. ELT가 구해 주는 건 앞으로 생길 필드다.

### CSV → NDJSON

컬럼 고정이 스키마 계약이 되어 필드를 조용히 버리던 지점을 없앤다. NDJSON은 줄 단위라
CSV처럼 스트리밍으로 읽히면서 레코드마다 키가 달라도 된다. 적재는 `.csv`도 계속 읽어
과거 파일 재적재가 가능하다.

### 압축: gzip이 아니라 zstd, 그리고 반드시 묶어서

실측(2026-09-05, 상세+회차 5페이지, 30~40편):

| 방식 | 편당 | 비고 |
|---|---|---|
| 개별 gzip | 91KB | PUT 500회 |
| 묶어서 gzip | — | **이득 0** (2252KB → 2281KB로 오히려 증가) |
| 묶어서 zstd-10 | **8.9KB** | PUT 1회 |

**gzip은 묶어도 소용없다.** 윈도가 32KB인데 페이지 하나가 400KB라, 두 번째 문서를
압축할 때 첫 문서의 보일러플레이트가 이미 윈도 밖이다. zstd는 윈도가 커서 노벨피아
페이지의 공통 부분(스크립트 172KB 포함)을 걷어낸다.

- **`window_log=23`(8MB)**: 128MB 윈도 대비 2%만 나쁜데 메모리는 16배 적다(9.0 vs 8.8KB).
- **레벨 10**: 19는 21MB/s라 4,719편에 86초가 걸리는데 결과 차이는 5%뿐(10은 408MB/s).
- **배치가 클수록 좋다**: 1편 67.5KB / 10편 9.1KB / 20편 5.7KB / 40편 4.0KB.

### 원본은 SQS로 보낸다 (S3 개별 업로드가 아니라)

한때 소설마다 S3에 하나씩 올렸는데, PUT이 소설 수만큼 들고 나중에 묶으려면 전부 다시
읽어야 했다. SQS로 보내면 consolidate가 전건을 들고 있게 되어 한 번에 묶는다.

**SQS 한도는 문제가 아니었다.** 실측으로 큐 기본 한도는 **1MB**이고(프로드 큐만 옛
설정 256KB), gzip+base64 페이로드가 **122KB**라 256KB에서도 절반만 쓴다. 비압축은
평균 753KB·최대 795KB라 1MB에 들어가긴 하지만 여유가 22%뿐이고 SQS 요금이 6.5배
(64KB 청크 13개 vs 2개)라 압축해 보낸다.

### 묶는 단위가 파이프라인마다 다르다

| | 묶는 곳 | 이유 |
|---|---|---|
| 데일리 500편 | consolidate | 비압축 368MB — 메모리 1024MB로 감당 |
| 공모전 4,719편 | **파서 배치(80편)** | 비압축 3.5GB — consolidate가 들면 5GB대 필요 |

공모전 파서는 SQS batch 80으로 트리거되므로 배치 안에서 묶으면 80편 × 753KB = 60MB뿐이다.
객체는 하루 59개가 되지만 편당 4KB로 떨어진다.

### 스크립트를 지우지 않는다

`<script>`를 제거하면 91KB → 42KB로 절반이 되고 크롤러 셀렉터도 전부 살아남는다(실측).
그런데 그건 "여기엔 값어치가 없다"를 미리 굳히는 것이고 ELT가 피하려는 바로 그 행위다.
차이가 월 $0.18이라 살 이유가 없다. 대신 **비밀값만 치환**한다 — 블록을 지우지 않고
값만 바꿔 구조를 보존한다(인증 세션 실측 편당 168건, 잔류 0).

### 연재 상태 판정

`p.in-badge` 안에서 **`b_*` class가 없고 텍스트가 있는** span의 텍스트다.
실측: `212573`=연재중단(#ea4a4a), `427211`=연재지연(#BAA576), `610`=없음.
처음엔 `b_`로 시작하는 class만 걷었는데 이 배지들이 통째로 사라졌다 — class가 `s_inv`
하나뿐이고 구분이 텍스트와 인라인 색으로만 되어 있다.

**아는 값으로 좁히지 않는다.** 모르는 상태(예: 완결)가 나오면 그 문자열이 그대로 남아야
한다. 상태 배지가 없으면 **필드를 싣지 않는다** — 빈 문자열을 쓰면 적재 Lambda의
`if v != ""` 필터에 걸려 '정상 연재'와 '판정 불가'가 구별되지 않는다.

**상태:** 데일리 적용·배포 완료(2026-09-05). 공모전은 구현·검증만 하고 **2026 공모전부터
적용**한다 — 2025 파이프라인은 `RAW_HTML_BUCKET`이 비어 있어 현행 동작 그대로다.

## 2026-09-27 — purge 는 상태 머신에서, 60초 기다린 뒤 보낸다

**결정:** 두 파이프라인 모두 SQS purge 를 Lambda 에서 빼 상태 머신 첫 단계(SDK 통합)로 옮기고,
purge 뒤에 **Wait 65초**를 둔다. 공모전 투입은 `send_message_batch` 의 `Failed` 를 확인해
실패시킨다. 공모전 상태 머신 제한은 3600 → 1200초.

**이유:** 2026-09-11 공모전 실행이 `TIMED_OUT` 났다. 작업 큐 송신 4,719 · 수신 4,130 ·
결과 4,120 — 599건이 **파서에 닿기 전에 큐에서 사라졌다.** 소비자 삭제(4,120 = 처리 수)·보존
만료(4일)·DLQ(없음)를 배제하면 남는 경로는 purge 뿐이고, CloudTrail 상 그날 SQS 관리 호출은
파이프라인 자신의 `PurgeQueue` 2건뿐이었다. 투입은 purge 요청 **0.3초 뒤** 시작해 8초 만에
끝났다. AWS 문서: 삭제에 최대 60초가 걸리고 *그 뒤에 보낸 메시지도 purge 중 삭제될 수 있으며*
60초 대기를 권장한다. 기존 `_wait_for_queue_empty` 는 "보이는 메시지 0" 만 봐서 원래 빈 큐에서
즉시 통과했다 — 기다린다는 로그만 남기고 실제로는 기다리지 않았다. 매일 같은 타이밍이었고
(9/10·9/11·9/12 CloudTrail 동일) 약 360회 중 한 번 걸린 것이라 **어느 날이든 재발할 수 있다.**
데일리도 같은 구조였다 — purge 19초 뒤부터 상세 결과가 큐에 들어왔다.

- **Lambda 안에서 `sleep` 하지 않는 이유**: 공모전 투입 Lambda 제한이 30초라 60초를 못 버틴다.
  Wait 상태는 실행 이력에 대기가 보이고 Lambda 과금도 없다.
- **`execution_id` 필터링으로 가지 않은 이유**: 결과에 실행 ID 를 싣고 이번 실행 것만 세면 시간
  가정 자체가 없어져 더 근본적이지만, 투입·파서·완료 판정·consolidate 넷을 고쳐야 하고
  "비우고 시작한다"는 구조가 바뀐다. 2026 공모전 파이프라인 설계 때 검토한다.
- **1200초**: 9월 정상 실행 최장 8분 12초 + 대기 65초. 멈춘 실행을 60분이 아니라 20분 만에
  실패로 드러내 알림을 앞당긴다. 데일리는 Express 재시도 연쇄가 길 수 있어 3600초 그대로.

**영향:** Wait 를 줄이거나 purge 를 Lambda 로 되돌리지 말 것. 배포는 상태 머신 → Lambda 순서
(OPERATIONS.md). 9/11 공모전 데이터는 복구 불가 — 결과는 9/12 purge 로 지워졌고 2025 파서는
원본 적재가 꺼져 있다.

**상태:** 유효

## 2026-09-27 — 즉시 알림은 Discord(멘션), 입구는 Lambda 하나

- **EventBridge API 대상 대신 Lambda:** API 대상은 connection 이 Secrets Manager 비밀을 만들고

- **멘션 방식:** 채널에 앞으로 자동화(CI/CD) 메시지도 올라오므로 채널 알림은 멘션만 받게 두고,

`resources`)도 함께 바꿀 것 — 안 바꾸면 조용히 감시가 끊긴다.

## 2026-09-27 — 브랜치 전략: trunk 기반, `main` = 배포 상태

**결정:** `main` 은 운영에 배포된 상태만 담는다. 작업은 `<type>/<요약>` 브랜치(feat·fix·refactor·docs·chore)에서
하고, PR 없이 로컬에서 rebase 후 fast-forward 로 합친다. 이미지 배포에는 `컴포넌트-v버전` 태그를 건다.

**이유:** 지금까지는 `main` 과 작업 브랜치(`pipeline/elt-raw-layer`)에 배포된 커밋과 안 된 변경이 섞여 있어,
"운영에 무엇이 돌고 있나"를 코드로 답할 수 없었다(예: 백엔드 Lambda 는 2026-04-13 배포본인데 작업 트리에는
그 뒤 변경이 쌓여 있었다). 1인 프로젝트라 리뷰 게이트(PR)는 비용만 들고, 이력을 일직선으로 두면 배포 단위가
커밋 단위와 맞는다. 태그는 ECR 이 최신 이미지만 남기는 운영(2026-09-27 `crawler:1.4.0` 삭제) 때문에 필요하다 —

## 2026-10-01 — 2026 공모전 수집: 2025 구조를 복제해 개막 당일 시작, 계산은 나중에

2025 스택은 그대로 돈다(사용자 결정). 화면의 대표 순위는 일간 순위로 한다(면접 D22 결론).
